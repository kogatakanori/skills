# Spec Comment Format

specはIssueの「意思決定の理由（Why）」をGitHubコメントとして記録する。
将来「なぜこの設計にしたのか」を確認できることが重要。

## コメント形式

specはファイルではなく、GitHub IssueのコメントとしてGitHub上に保存する。
コメントの先頭には必ず識別子を付与する：

```
<!-- arc:spec -->
```

この識別子により `/arc-designing` や `/arc-planning` がspecを自動的に取得できる。

## セクション構成

### Context（背景・Why）
- このIssueが生まれた背景・課題
- ビジネス上・技術上の動機
- 現状の問題点

### Goal
- この機能で達成したいアウトカム（測定可能であれば望ましい）
- ユーザーや開発者にとってのメリット

### Non-Goals
- 明示的にスコープ外とすること
- 将来のフェーズに先送りすること

### ADR（Architecture Decision Record）

#### 採用したアプローチ
- 具体的なアーキテクチャ・実装方針
- 使用するライブラリ・フレームワーク・パターン

#### 検討した代替案と却下理由
それぞれの代替案について：
- 案の概要
- 却下理由（技術的制約・コスト・複雑性・既存コードとの相性など）

#### トレードオフ・リスク・懸念点
- この設計がもたらす制約
- 既知のリスクと軽減策
- 将来の変更に対する影響

### Design
（`/arc-designing` が別コメントとして投稿する）

なぜ実現可能 / 条件付きで可能 / 困難かの理由を記録する。
