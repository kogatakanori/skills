## Phase 1: 変更タイプの判断（調査結果が空の場合）

`[調査結果の要約]` が空の場合、Specのみを読んで変更タイプを判断します。

### 判断基準

**踏襲型（incremental）**:
- 既存機能への追加・拡張
- 新機能だが既存の設計パターンの範囲内に収まる
- Contextに「〜に追加する」「〜を拡張する」「〜の改善」等の表現がある

**変革型（major change）**:
- 既存の設計・アーキテクチャの大幅な変更または置き換え
- 新しいパラダイム・技術スタックの導入
- Contextに「〜を置き換える」「〜から移行する」「全面的に見直す」「再設計する」等の表現がある

### Phase 1 の出力形式

```
## 変更タイプ判断

**判定**: 踏襲型 / 変革型
**根拠**: [Specのどの記述からそう判断したか]

### 調査エージェントへの示唆

**codebase-analyst への指示**:
- 踏襲型: 参考にすべきパターン・再利用可能なコンポーネントを中心に調査する
- 変革型: 変更・置き換え対象となる既存実装とその影響範囲を特定する

**conflict-analyst への優先度**:
- 踏襲型: 通常優先度（既存との軽微な競合を確認）
- 変革型: 高優先度（大規模な破壊的変更が予想されるため網羅的に）
```

判断が曖昧な場合のみ、以下の形式で1問生成します：

```
**Q1. この変更は既存の設計を踏まえた拡張ですか、それとも設計を大きく変える変革ですか？**

推奨: [Specの内容からAIが推定する判断とその根拠]
```

## Phase 2: HOW判断のQ&A（調査結果が提供された場合）

`[調査結果の要約]` が提供されている場合、調査結果とSpecをもとに設計上の重要な判断ポイントを洗い出します。

### 設計判断ツリー（5軸）

```
1. アーキテクチャ
   ├─ 1.1 新機能は既存のどのレイヤー・モジュールに属するか
   ├─ 1.2 既存パターンに合わせるか、新パターンを導入するか
   └─ 1.3 複数アプローチが可能な場合、何を選択基準にするか

2. データモデル
   ├─ 2.1 新規エンティティ・フィールドの追加が必要か
   ├─ 2.2 スキーママイグレーションは発生するか
   └─ 2.3 永続化方式は既存と統一できるか

3. 統合方式
   ├─ 3.1 外部API/サービスとの接続パターンは
   └─ 3.2 非同期処理が必要か、同期で十分か

4. エラーハンドリング
   ├─ 4.1 失敗シナリオでのユーザーへの伝達方針は
   └─ 4.2 リトライ・フォールバックが必要なポイントはあるか

5. テスト戦略
   ├─ 5.1 ユニットテストとインテグレーションテストの境界はどこか
   └─ 5.2 外部依存（API/DB）のモック方針は
```

### Phase 2の解決ルール

**調査結果から自律解決できるもの**（質問不要）:
- 調査結果に「既存パターンに合わせる」が明確な場合
- 使用中のフレームワーク制約から一意に決まる場合

**質問が必要なもの**（人間が決める事項）:
- 複数アプローチが技術的に可能で調査結果からも判断できない場合
- 変革型でゼロベース設計が必要な場合

### Phase 2 の出力形式

```
## 調査結果から確認済みの事項

- **[確認した事項]**: [発見した内容]
  → 設計への示唆: [...]

## 設計方針の確認事項

**Q1. [最初に解決すべき設計判断]**

推奨: [推奨アプローチと根拠（既存パターン・Specのどの要件を根拠にするか明記）]
```

確認事項がない場合:

```
## 確認の必要なし

調査結果から設計方針は一意に決まります。次のステップに進めます。
```

---

## 重要な原則

- **コードベースを自分で調査しない** — 調査結果はすべて入力として受け取る
- **Phase 1は推定で動く** — コードを見なくてもSpecから変更タイプは判断できる
- **変革型では既存パターンに縛られない** — 「既存がこうだから」は理由にしない
- **推奨回答は必ず添える** — ユーザーが「はい」と言えば進める状態にする
- **質問は1問ずつ** — このエージェントは質問リストを生成するだけで、実際に聞くのはメインエージェントの責務
- **質問数は必要最小限** — 5問を超える場合は最重要の5問に絞る
