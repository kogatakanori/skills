# Spec Comment Format

specはIssueの「意図（Why / Who / What / Use Cases / Constraints / Domain Model）」をGitHubコメントとして記録する。
**HOW（実装方法・技術選択・スコープ）は一切含まない**。それらは `/arc-designing` フェーズで決定する。

## コメント識別子

specの先頭には必ず以下の識別子を付与する：

```
<!-- arc:spec -->
```

この識別子により `/arc-designing` や `/arc-planning` がspecを自動取得できる。

## セクション構成（7セクション）

### Context（Why）
- このIssueが生まれた背景・課題
- ビジネス上・技術上の動機
- 現状の問題点

### Who（誰が使うか）
- この機能を使うユーザー・ステークホルダーの一覧
- 各ユーザー種別の役割・技術レベル・利用文脈を記述する
- 複数のユーザー種別がある場合、全員を列挙する

### Goal（What）
- 達成したいアウトカムを「〜できる」「〜になる」形式で記述
- 抽象的すぎないこと（何をもって達成とするかが判断できる粒度）

### Use Cases（ユースケース）
- GoalをどのようなシナリオでUserが利用するかを具体的に記述
- 形式: `[ユーザー種別] が [状況・前提] のとき、[操作] をすると、[期待結果] になる`
- 各GoalにUCが最低1つ存在すること
- エラー・例外・境界ケースも記述する

### Acceptance Criteria
- 各Goalに対するビジネス視点での完了条件
- 「〜した場合、〜となること」の形式
- テストまたは人間の評価で確認できる具体的な記述にする

### Constraints（ビジネス制約・不変条件・品質要件）
守らなければならないビジネスルール・不変条件・品質の下限。「HOW」には踏み込まない。

Constraintsは2種類ある：

| 種別 | 例 |
|------|---|
| **条件・選定型**（クライアント指定・技術環境・法規制） | `TypeScriptで実装すること` / `AWSのみ使用すること` / `GDPR準拠を維持すること` |
| **非機能要件型**（品質の下限・数値で表現できる） | `一般ユーザーの操作は3秒以内に完了すること` / `同時100ユーザーに耐えること` |

非機能要件型は具体的な数値・基準値で書くこと。

### Domain Model（ことばの定義）
- この機能で登場するエンティティ・概念の定義
- チーム全員が同じ言葉で話せるようにする
- コードベースで既に使われている用語と一致しているか確認する
- 独自の用語・概念がない場合は「なし」と記載

## specに含めないもの

| 含めないもの | 代わりにどこで決める |
|---|---|
| スコープ（In/Out of Scope） | `/arc-designing` |
| 実装アプローチ・技術選択 | `/arc-designing` のADR |
| Non-Goals（明示的なスコープ外） | `/arc-designing` のスコープ定義 |
| 実現可能性の判断 | `/arc-designing` |
