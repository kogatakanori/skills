# Docs File Format

docsファイルは機能の「現在の仕様（What）」を記録する。
常に最新の状態に保ち、開発者が機能の使い方・仕様を確認できるようにする。

## ファイル名規則

```
docs/feature-name.md
```

例: `docs/user-authentication.md`

タイムスタンプやissue番号は不要。常に最新版が上書き保存される。

## フロントマター

```yaml
---
title: User Authentication
issue: "#42"
last_updated: 2026-05-06
---
```

`issue` フィールドにはこの機能を作成したIssue番号を記載する。
specはIssueコメントに保存されているため、`spec:` フィールドは不要。

## セクション構成

### 概要
- この機能が何をするか（1〜3文）
- どの問題を解決するか

### 使い方
- 具体的な使用例（コードスニペット・コマンド例）
- 主要なユースケースをカバーする

### 仕様
- 動作仕様の詳細（入力・出力・副作用）
- 設定オプションがあれば一覧
- エラーケース・制約事項

### ADR
```markdown
## ADR

この機能の設計判断・代替案の検討・採用理由は [Issue #NNN](<issue-url>) を参照。
```

specのWhy・設計判断はIssueコメントに記録されているため、docsにはIssueへのリンクのみ記載する。
既存機能を修正した場合は、このセクションを新しいIssue番号で更新する。

## 更新タイミング

実装の各タスク完了後、実装内容に合わせて更新する。
設計の理由（Why）はdocsに書かない。仕様（What/How）のみ記述する。
